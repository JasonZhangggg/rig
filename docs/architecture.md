# How Rig is built

## The pieces

```
 Website (apps/web)            Desktop app (apps/desktop, Tauri)
   CloudClient                   LocalClient ──────────────┐
      │                              │   Rust: SQLite store, keychain token
      │ cookie                       │ bearer token        │ named pipe (private)
      ▼                              ▼                     ▼
   Rig server (apps/server) ◄── sync ──┘            RigHelper.exe (admin)
   accounts · PC snapshots · chat · manuals         LibreHardwareMonitor · WMI · fixes
```

Both apps mount the same `RigApp` from `packages/ui` and differ only in the client they pass in. Every client implements one interface, `RigClient` (`packages/core/src/client.ts`):

- `DemoClient`: two made-up PCs in memory, each following a weekly schedule of work, evening games and background tasks. Powers the website's demo and the UI tests.
- `LocalClient`: this PC, through the helper. History and the change log are kept on disk. When signed in it uploads a snapshot every five minutes and after each change, and reaches the account's other PCs through the server.
- `CloudClient`: the website. Reads what each PC uploaded. It can't make changes; those happen in the app on the PC itself.

The PC view the screens draw is built by one function, `buildPC` (`packages/core/src/view.ts`), from the helper's raw readings. The desktop runs it live and uploads the result, so the website shows exactly what the app shows.

## The server

`apps/server` is one Cloudflare Worker (Hono) with a Postgres database (Neon in production, reached through Cloudflare Hyperdrive with its query cache turned off; queries go through Kysely, which Better Auth uses too). Each request opens its own connection pool and closes it after the response. It serves the website's files and, under `/api`:

- **The address.** The site is `https://rigpc.app` (`WEB_ORIGIN`, also Better Auth's base URL, the desktop sign-in page and the updater's download links). The Worker also answers at its `workers.dev` address, which installed apps up to 0.1.4 call; a page opened there, or on `www`, moves to the site (the last route in `apps/server/src/app.ts`), so sign-in cookies stay on one site.
- **Accounts** with [Better Auth](https://better-auth.com): email and password on the website, Google when it's configured, and the desktop sign-in. Sign-in attempts are limited per caller, by the address Cloudflare puts in `cf-connecting-ip`; the counts are kept in the database so they hold across Worker instances. The desktop asks for a code (`/api/auth/device/code`) and opens `/app/?user_code=…`, where the person checks the code and approves. The app then gets a bearer token, kept in Windows Credential Manager.
- **PCs**: the desktop uploads its view, settings, change log and new history points (`PUT /api/machines/:id/sync`). The website reads them back. A PC is keyed by account and machine id, and counts as online when it synced in the last 12 minutes. Name and color can be changed on either side; whichever changed last wins.
- **Your data**: `GET /api/me/export` downloads the account's PCs with all their history, recordings, the list of their manuals (not the page text) and chat use as one JSON file (shaped by `makeExport` in `packages/core/src/export.ts`, the same file the desktop app makes for this PC when signed out). `DELETE /api/me` with `{ "confirm": "DELETE" }` removes the account, its PCs, history, recordings, manuals and their pages, chat use, desktop sign-in codes and sign-ins in one transaction.
- **Chat** (`POST /api/chat`, streamed): Claude (`claude-opus-5-5`) gets the PC's readings and settings and the list of its manuals, searches the manuals Rig has read (see Manuals), can search the web for maker pages, and has three tools for changes. `propose_change` shows a change card; the server checks each step (see below) and, for a fix, against what's actually on that PC (the power plan, startup app or display has to exist) before the person sees it. `drive_app` looks at a control in an app's window and proposes a change to it (see Screen control). `show_steps` shows numbered steps for things only the person can do. One card per answer, and nothing changes until the person approves in the app on that PC. Each account gets a daily allowance of questions.

How to put it online: [deploy.md](deploy.md).

## Changes are safe by construction

A change is a list of steps. A step is one of three kinds. The types are in `packages/core/src/change.ts`.

- A **fix** from the fix catalog (`packages/core/src/actions.ts`: power plan, startup apps, Game Mode, visual effects, processor speed cap, screen refresh rate).
- A **command**: a PowerShell change request with `does` (Claude's sentence), `read` (a script that only looks), `run`, an optional `undo`, and `touches` (the registry keys, files, services and devices it changes). Commands reach settings the catalog doesn't name. For the common ones (a registry value, a service, a firewall rule, a policy, a device, a driver, an app) a shorthand writes the command from a few typed fields (see Shorthands).
- A **native op**: a change PowerShell can't make safely, which the helper's own code makes: a graphics driver setting, values in a settings file, or a control in an app's window (see Native ops).

1. **Rig works out the risk, not Claude.** `checkStep` (`packages/core/src/check.ts`) splits each script into the commands it runs and looks each up in one table, `packages/core/src/rules/commands.json`. The table gives plain words for the card, a tier and whether admin rights are needed. Tier 0 only looks, tier 1 is a catalog fix or a native op Rig puts back exactly, tier 2 is a general change and tier 3 can't be undone or lowers a protection. The never list (new accounts, administrators, remote access, Defender exclusions, trusted certificates, the hosts file, what starts with Windows, boot settings and the like) is refused, as is anything the checker can't classify: dynamic names, `iex`, encoded commands, .NET calls, wildcards in paths, other machines. The server checks every step before the person sees it, and the helper checks again with Windows PowerShell's own parser against the same table. The shared vectors in `rules/vectors.json` are run by both.
2. **Rig looks first.** Chat can read the PC live with `read_pc` (registry, CIM classes, tier 0 cmdlets and scripts, graphics driver settings) and look in an app's window with `drive_app`. The server ends the stream with a `reads` event and a signed resume (`CHAT_STATE_SECRET`); the app runs the reads through the helper as the signed-in person and continues the chat. After Rig reads text from outside (a web page, a manual, a recording, script output, a look that isn't clean), the chat is marked, and a marked chat can't be offered a tier 3 step.
3. **The card shows what Rig found, not what Claude said.** Tier 1 keeps the before and after table. A tier 2 card is amber: Claude's sentence labelled as Claude's, what `read` printed, the commands in plain words from the checker, each touch with its current value, the undo line, and the full scripts one tap away. It needs Review, then Apply. A tier 3 card is red, one step per card, says first what can't be undone, and needs a typed word. A refused step has no Apply; it offers steps for the person instead.
4. **The helper holds the approval.** Commands and native ops go one way, in `helper/RigHelper/Commands.cs`: `step.check`, `step.preview`, `step.apply`, `step.undo` (the old `command.*` names still answer, for an app from before native ops). Preview checks the step again, reads its state now and stores a `Pending` under a single-use nonce that expires in 10 minutes: the step, its verdict, what it read and each touch as the card showed it. Apply sends only the nonce. It reads a native op's state and each file touch again first, and nothing runs when either differs from what the card showed. What's approved is the whole step: `stepHash` in `change.ts` and `HelperStep.Hash` in the helper give the same fingerprint (`rig-command-1` for a command, so older apps still agree, `rig-step-1` for anything else). Preview answers with the one it stored, and the app shows the card only when its own agrees. A step that needs admin rights is approved again behind Windows' own permission prompt (`--approve-step`), outside the app's window. Tier 2 and 3 changes have a daily limit per PC (12), kept in the helper.
5. **Snapshot, run, verify.** Before running, the helper saves the touched registry values (typed, with absent values, the person's hive by SID), files and service settings, and makes a restore point where System Protection is on. It watches the never-list places before and after; a write there, or a failed run, is put back at once and reported as rolled back. It runs `read` again to show before and after.
6. **Undo puts back what was saved, then runs `undo`.** If something else changed those places since, undo stops and asks before overwriting. What Rig couldn't save is named on the card and in the change log, with the restore point as the last resort.
7. Fix steps keep their own undo calls. If one step of a multi-step change fails, the steps before it are put back, and the person is told nothing changed. Undo replays the stored undo calls in reverse order. Redo replays the originals.

Rig changes nothing on its own: drivers and other settings outside the catalog only change through a step the person approved.

## Shorthands

For the common changes the chat fills in a few typed fields and Rig writes the PowerShell (`packages/core/src/shorthand.ts`, one file per kind in `shorthands/`). What comes out is an ordinary command step: checked, run, snapshotted and undone like one Claude wrote, so a shorthand adds no new way to run anything. Every limit a shorthand holds to is also a rule in `commands.json`, with examples in `rules/vectors.json`, so a hand-written command meets the same limit. A program's rules (pnputil, winget) list the arguments each form may take (`params`, `single`, `fit`), and any other argument is refused.

| Shorthand | What it does | Undo | Tier |
|---|---|---|---|
| `registry`, `service` | One registry value; how a service starts. | The snapshot. | From the checker. |
| `firewall` | Adds one rule, named `Rig-` and a fingerprint of the request, or turns a rule on or off by its name. A rule that lets connections in needs a program or ports, never opens the remote-access and file-sharing ports (22, 135, 139, 445, 3389, 5985, 5986) and never names a program in the Windows folder. Rules picked by group or by several names are tier 3, and by a pattern refused. | Deletes the rule Rig added, or turns the rule back. | 2; 3 for letting connections in on public networks. |
| `policy` | One value under `Software\Policies`, for the whole PC or this account. Stops before writing on a PC joined to a domain or enrolled in device management. Runs no `gpupdate`. | The snapshot. | 2, with admin rights. |
| `device` | Turns one device off or on by its instance id. Stops when it's already that way, and won't turn off a part Windows needs or the last working display, keyboard or mouse. That guard is only in the script, so the rules put every `Disable-PnpDevice` at tier 3. The touch is the device, which the helper reads as on or off for the card, before and after. | The opposite. | 3, both ways round. |
| `driver` | Installs a driver from a `.inf` already on the PC with `pnputil /add-driver`, after checking its catalog is validly signed. The read shows the signer and both files' hashes; both files are touches, and one swapped after the card was shown is refused. The change script doesn't write them, so the card says undo has nothing to put back and offers no Undo. Nothing is downloaded. | None; the restore point is the last resort. | 3. |
| `app` | Installs, updates or uninstalls one app with winget, by its id, from winget's catalog or the Microsoft Store, never a file or a link. Runs as the person, never with admin rights (`person` in its rules row), for up to 30 minutes (`minutes`). An install or update accepts the app's licence, and the card says so. What an installer is expected to change (a rule's `expects`, like a new service) is listed on the result, not put back; anything else on the never list rolls it back. | Install: uninstalls. Update with `from`: uninstalls, then installs that version again. Uninstall: none. | Install 2; update and uninstall 3. |

## Native ops

A native op is a change PowerShell can't make safely. Each kind is one member of `NativeOp` and one entry in `nativeOps` (`packages/core/src/change.ts`: its canonical form, tier, reasons, title, touches, never-list words and card rows), one entry in `nativeParts` for the card (`packages/ui/src/components/change/native.tsx`), and one class in the helper that implements `INativeStep` (`helper/RigHelper/NativeSteps.cs`: `Check`, `Preview`, `Apply`, `Verify`, `Undo`). The kinds are `gpu`, `fileEdit` and `screen`, and `selftest`, which the helper knows only inside `--selftest`.

- **Rig's code sets the tier and the touches.** The model sends only the op. The helper's `Check` runs before the op is stored, again before it runs and again before its undo, and must give back the same op, or the step is refused as changed. Touches are held to the never list like a command's. A native op never needs admin rights.
- **A worker makes it, as the person.** The helper may have admin rights, so it never makes a native op itself. It starts a worker: the same program with `--native-worker`, using the Rig app's own Windows sign-in (`Person` in `CommandHost.cs`), on the person's desktop, so it can do nothing the person couldn't. Preview, apply, the read back and undo each get a fresh worker, and what it answers is read as outside data, like a script's output. A helper running with no desktop (as a service) refuses.
- **The same guards as a command.** Snapshot the touches, a restore point for tier 2 and 3, the never-list places read before and after, then the worker's `Apply` and a fresh worker's `Verify`. A change that didn't hold, or a never-list write, is put back by the op's own `Undo` first, then the snapshot.

## Screen control

Some settings live only behind an app's buttons, like NVIDIA Control Panel's output range or a Settings page's switch. A `screen` step sets one control there. The code is `packages/core/src/screen.ts`, `helper/RigHelper/Screen.cs` and `ScreenWalk.cs`; the rules are under `screen` in `commands.json`.

1. **Look, then change.** The chat's `drive_app` tool has two stages. `look` names the app and the controls on the way. It goes to the PC like a read: the worker walks there and reads the control, changing nothing. The helper keeps what it found (the program and its signer, each control by name, type and automation id, the value, its choices or range) in memory for 30 minutes under a `lookId`, and answers with the path, the value and its choices in the app's own words. `change` names only `{ lookId, to, does }`: a value the look offered, never where to press. The look rides on the proposal, so the app checks the step against it too.
2. **Which apps.** From the chat, an app on Rig's list (NVIDIA Control Panel) or a Settings page on its list, like `ms-settings:display`. The helper also takes a program by its full path under Program Files or Windows, used only when it's already open. Browsers, mail and chat apps, terminals, Windows' own admin tools, password managers, remote-control tools, installers and Rig itself are refused by file name, before anything starts and again by the window's own program. A listed app has to run from its own folders, as its own package, signed by its maker; the helper reads all of that from the window's process, not from the worker.
3. **What a look may do.** It walks by selecting tabs and tree rows, nothing else. It never picks a row of a list or a drop-down (in some apps that row is the setting), never acts on anything inside web content, and never walks through a control named like `neverNames` (password, sign in, payment, terms, delete, reset, uninstall, administrator and the like). Each hop must match exactly one control of the app's own process, found by what it is, never by where it sits; otherwise the walk stops and says what it saw. The only calls that act are UI Automation's Select, Expand, Collapse, Toggle, SetValue and Invoke. Nothing types, moves the mouse or clicks a place on the screen. A classic Windows drop-down, which UI Automation can't set, takes its approved entry by the three messages its own list sends, and only in an approved change.
4. **The clean-look rule.** A look's text is someone else's words unless the look is clean: the window's program is the app, installed where only admins can write, signed by its maker, and not a program that shows documents (`contentHosts`); the control and its choices are a button, checkbox, drop-down, list item, radio button or slider; and nothing on the way is web content. An unclean look marks the chat as having read outside text, and no change can come of it. A clean one doesn't mark the chat.
5. **The Stop bar.** Every walk shows a bar on top of the screen that says what Rig is doing, with a Stop button. The walk also stops when another program's window opens or Windows asks for permission. After Stop nothing in the window is touched or read again, not even to put it back, and the result says Rig stopped part way and offers undo.
6. **Commit buttons.** After setting the control, an approved change presses the app's own Apply button, or OK when the window also has Cancel (the names in `commit`, in several languages). It stops before setting anything when an Apply button is already enabled (changes are waiting that the card didn't show), and before pressing one when any other control it can read has moved. When a button not on the list became enabled and none on it can be pressed, the change isn't finished and is put back, except in Settings, which applies each change at once.
7. **Always tier 3.** Rig can't see what the app writes, and undo walks the same path again with the old value, which can miss if the app changed. The red card shows the app, the path, and the value now and after, labelled as the app's own words, and needs the typed word. Apply reads the control back, and a value that didn't hold is put back.

## Graphics settings

The `gpu` native op sets one NVIDIA setting to one value from Rig's table, `packages/core/src/rules/gpu.json` (15 settings: low latency, frame rate cap, vertical sync, power mode, texture filtering, anti-aliasing, G-SYNC and others), for one game by its program file name or for the whole PC. Never a free id or value, and never for one of Windows' own programs. `packages/core/src/gpu.ts` and `helper/RigHelper/Gpu.cs` read the same table.

- **NVIDIA only.** Writes go through NVIDIA's driver settings database (DRS), the one NVIDIA Control Panel's 3D settings live in, through Rig's own bindings (`NvApi.cs`), in the worker. Reads are `read_pc` kind `gpu`, made by the worker too. For AMD and Intel the read only checks the maker's signed DLL and says Rig can't read its settings yet.
- **Undo is per setting.** Apply notes, for each id it sets, whether the profile held it and whether that was NVIDIA's value or the person's own, and whether Rig made the game's profile. Undo sets each back and takes out only what Rig added, so other settings in the profile stay. That's exact, so every setting is tier 1. Every read back loads a fresh session from the driver.
- **Loading the driver's DLL.** `nvapi64.dll` is loaded only from System32 by its full path, with its own dependencies looked for in System32 alone, and only once Windows says its signature is valid and the signer is NVIDIA. Nothing is loaded by a bare name, so a DLL planted next to the helper is never picked up.

## Settings files

The `fileEdit` native op changes values in a program's or game's own settings file, and nothing else in it (`packages/core/src/fileEdit.ts`, `helper/RigHelper/FileEdit.cs`).

- **JSON and INI.** `.json`, `.jsonc` and `.cfg` as JSON; `.ini` and `.cfg` as INI (key=value lines under `[sections]`). Each edit names its value's place: JSON keys and indexes, or an INI section and key, with `add: true` for a key the file doesn't have yet. At most 20 values, in a file of at most 1 MB.
- **Byte splice.** The worker reads the file as the person with a small reader of its own (JSON with comments and trailing commas; INI with `;` and `#` comments) and replaces only each value's bytes, so the encoding, quoting and line endings stay as they were. It writes a new copy beside the file and swaps it in, as the person. A file that is a link to another is refused.
- **Tiers.** 1 in the person's own folders; 2 elsewhere, or when it adds a key; 3 for the settings of developer tools and coding agents, which can name a program to run. Refused: sign-in, key and browser profile files (`fileEdit.never` in `commands.json`, checked first so the card gives that reason), anything on the never list, and programs, scripts and shortcuts.
- **The card** shows each value before and after and the lines that change. Preview reads the file's fingerprint, and apply refuses if it changed since. The file is the op's touch, so undo puts the snapshot back.

## Left out for now

- Changing AMD and Intel graphics settings. Rig reads neither yet.
- Drivers from Windows Update or a maker's site: only a signed `.inf` already on the PC.
- YAML and XML settings files.

## The helper

`helper/RigHelper` is a .NET 8 program. The app starts it once through the Windows admin prompt (`ShellExecuteEx` with `runas`). If the person says No, it starts without admin rights and Rig shows which readings are missing.

Talking to it stays private: the app makes a named pipe with a random name that takes one connection, then checks the connected process is the helper it started. The helper checks the pipe belongs to its parent and quits when the app does. Requests are JSON, one per line: `hello`, `inventory`, `facts`, `snapshot`, `apply`, `storage` (see My PC), and two that only read: `events` (errors, crashes, driver resets and unexpected shutdowns from the Windows event log, at most 300 from the last 30 days) and `processes` (the busiest apps since the last call). Changes go through `step.*` and `screen.look` (see Changes are safe by construction).

`RigHelper.exe --selftest out.json` reads everything once and writes it to a file. CI runs this on a Windows runner.

CPU temperatures and motherboard fans need LibreHardwareMonitor's PawnIO driver. Graphics cards, drives and batteries read without it. The installer installs PawnIO (a pinned, signature-checked copy) and uninstalling Rig removes it only if Rig put it there.

Each call to the helper has 20 seconds, one at a time. A step's check, preview or look gets about 5 minutes, and an apply or undo about 68 minutes, since a winget run may take 30 minutes and a rollback runs its undo too (`limit` in `apps/desktop/src-tauri/src/helper.rs`). A call that runs out returns an error; three in a row and the app restarts the helper. A WMI query inside the helper gives up after 5 seconds.

## Starting up, and the logs

`LocalClient.start()` (`packages/core/src/local.ts`) reads the PC in named steps: saved data, parts, settings, saved history, then the first sensor reading. Settings are allowed to fail; the next tick tries again. A failed start is tried again on the next call. If the first read takes more than 45 seconds the screen says which step it's stuck on and offers Try again (`STALL_MS` in `packages/ui/src/state.tsx`).

Which PC an id belongs to is only known once this PC's parts are read, so the desktop client waits for that before sending an id to this PC or to the account. The screen reopens the PC it showed last, and without that wait a saved id looked like another PC on the account.

The desktop logs to `%LOCALAPPDATA%\app.rig.desktop\logs\Rig.log` with `tauri-plugin-log`: each startup step with its time, each helper call, each server call with status and time (ids and codes left out), sensor failures and the updater. Server calls give up after 30 seconds. [development.md](development.md#when-something-goes-wrong) says how to read it.

## My PC

My PC has three tabs, each at its own address so a link or Ctrl K opens the right one. The sidebar keeps My PC highlighted on all three (`homeOf` in `packages/ui/src/components/Shell.tsx`).

- **Parts** (`#pc`, `packages/ui/src/pages/PCPage.tsx`): the 3D view with numbered labels and the parts list. Picking a part shows its readings, specs, manual and drivers. Its Upgrade tab links to the matching kind of part on Upgrades.
- **Upgrades** (`#upgrades`): see Upgrades below.
- **Manuals** (`#manuals`): see Manuals.

**The storage map** opens first on the storage part (`packages/ui/src/pages/drives/StorageMap.tsx`, data from `driveMaps` in `packages/core/src/drives.ts`). Each drive is a block split by what fills it (Windows, Apps, Games, Your files, Page and sleep files, Other, Free), with its health beside it: Windows' own check, life left, data written, hours powered on, errors it couldn't fix and its temperature. What Windows doesn't report for a drive is listed under it, never guessed.

- **Volumes go on drives by disk number** (`MSFT_Partition`). A helper older than 0.1.8 doesn't send it: with one drive every volume goes on it, otherwise they show apart as "Other drives".
- **Folder sizes come from the helper's `storage` request**, which never waits on the disk. It answers from a scan kept in `%ProgramData%\Rig\storage.json` and starts a new one on a background thread at the lowest priority (Windows' background mode, so disk reads yield too) when there is none, it's over a day old, or the person presses Measure again. Each drive's walk stops after 5 minutes. Games are found from Steam, Epic, GOG and Xbox libraries; cloud-only files aren't counted. The app asks every 30 minutes, every 15 seconds while a scan runs (`readStorage` in `packages/core/src/local.ts`).
- **Shares never add up past what's used.** Windows shares files between its folders, so counted folders can exceed the drive; then every share is scaled down. What wasn't counted (restore points, the recycle bin, folders Windows keeps locked, Game Pass games in WindowsApps) is Other.
- **Health readings** come from `MSFT_StorageReliabilityCounter` (wear, hours, uncorrected errors), read at most once an hour. Hours and errors need admin rights; without them the map says so.

## Upgrades

Upgrades works like PCPartPicker, except the build is the PC you already own, so every check runs against the parts Rig read. The feature map, and where real prices would come from, is in [upgrades.md](upgrades.md).

- **The rules are in `packages/core/src/shop.ts`.** `hardwareFacts` turns the inventory into what the checks need (socket, memory type and free slots, free M.2 slots, BIOS date, typical power draw). `fitOf` gives each part one of three answers, Fits, Check first or Won't fit, with the reason. Things Windows can't see, like card length against the case, are Check first, never a guess. Power supply wattage is asked once and kept per PC on that device.
- **The catalog and every price are demo data.** `demoCatalog` has made-up shops (Northwind, Contoso Parts, Fabrikam), and every price on screen sits under a "Demo prices" label. No ratings are shown. Parts have a slot for a photo, filled only from a shop feed that licenses it; the demo has none and shows the kind of part's icon.
- **Best Buy, when the server has `BESTBUY_API_KEY`** (`apps/server/src/retail.ts`): the server looks each catalog part up in Best Buy's Products API and keeps a listing only when its name holds the same model, size and memory type (`sameRetailPart` in core), so a part never borrows another's photo or price. A match replaces that part's demo price and photo with Best Buy's, with a link to its page and "Photos and prices marked Best Buy come from Best Buy" where they show. Listings are kept in memory for 12 hours (Best Buy allows 72), looked up 4 a second (it allows 5), and the key never leaves the server. Without the key nothing is looked up. The desktop allows images from `*.bbystatic.com` for these photos.
- **The server serves it** at `GET /api/machines/:id/shop`, built from the PC's last upload. Each client has `shop(machineId)`; the desktop asks the server.
- **The screen** (`packages/ui/src/pages/upgrades/Shop.tsx`) leads with a free fix if Rig found one, then Rig's pick, then the kinds of part that can change. Each kind of part can be searched (`matchesQuery`) and filtered by maker, and a search names matches in other kinds. A laptop only offers storage. A part Rig doesn't list can go on the list with the person's own price, marked Not checked. "Your list" totals the parts you added, with the change in power draw, and is kept per PC on that device.

## Logs and recordings

When the chat can't tell what's wrong from the latest readings, it records. A recording keeps temperatures, load, fan speeds, the busiest apps and the Windows events that land while it runs, for 1 to 180 minutes. It only reads.

- **The model and the summary are in `packages/core/src/recordings.ts`.** A capture kind is one entry in the `captures` table and an event kind is one entry in `eventRules`; adding either is a table entry. `summarise` is pure: it finds sustained heat, a part pinned at full load, sudden drops and each Windows event, with the readings around it. The Logs screen and the chat both read that one summary, so the charts and Claude's answer agree.
- **The desktop runs it** (`recorder.ts`). It saves as it goes, so a recording survives the app closing or the PC crashing, which is often the thing being recorded, and it reads the event log when time is up. The newest 20 stay on the PC.
- **The chat has two tools**, `start_recording` and `read_recording`. On the desktop the recording starts at once. From the website the server stores the request and the desktop picks it up on its next upload, up to about five minutes later; the chat says so. When it finishes, the desktop uploads it, shows a Windows notification, and the chat offers "See what Rig found".
- **The server keeps them per account and PC** (`0003_recordings.sql`): the 20 newest for 90 days, one running at a time, and a request nobody picked up in a day is closed.
- **The Logs screen** has two views, each with its own address: Events (`#logs`, `packages/ui/src/pages/Logs.tsx`) and Performance (`#history`, `pages/History.tsx`). The Games view (`#games`) is no longer a tab; Ctrl K still opens it. Events lists Windows events by day with a kind filter, the recordings, and one recording with its charts, what Rig found marked on them, and "Ask about this". Performance is laid out like Task Manager's Performance tab with HWMonitor's sensor list: a list of parts down the side (processor, graphics card, memory, storage, motherboard, fans), each with its reading now and a sparkline, and for the picked part one chart at a time. A list at the top of the part (`Picker` in `History.tsx`) groups every sensor the part reports by kind (temperatures, usage, speeds, power, voltages, fans and so on, `sensorKinds` in `packages/core/src/sensors.ts`), with a filter to type in. Picking a whole kind that Rig logs (temperature against the safe limit, usage, memory in use, fastest fan) shows the figures (highest moment, when busy, at rest) and its chart over Live, Day, Week or Month; picking one sensor, like the hot spot or core 3, or a kind Rig doesn't log, charts the readings that arrived since the page opened. Under the chart, that kind's sensors with now, lowest and highest, the picked one marked. A search above the parts (`findReadings`) finds any reading on any part from a few words, like "core 3", "hot spot" or "usage", grouped by part. Each history point keeps processor and graphics load and memory in use (averaged over the window) and the warmest drive and motherboard temperature (`HistoryWindow` in `packages/core/src/history.ts`, columns added by migration `0005_history_parts.sql`). The sensors come from `PC.readings`, built by `buildPC`; Live draws `livePoint(pc)` as each update arrives, for the last five minutes the page was open. Each part opens with the few readings worth a glance (`keyReadings` in `packages/core/src/sensors.ts`, a rule table per part matched against LibreHardwareMonitor's sensor names: package, hottest and fastest core, power and core voltage for the processor; core, hot spot, video memory, clock, power and fan for the graphics card; temperature, life used and transfer rates for drives; socket, power delivery, chipset and rail voltages for the motherboard). With usage picked, the processor also gets a tile per core (`coresOf`: load, each thread, clock, temperature and power, P-cores before E-cores). When the helper runs without admin rights or without the PawnIO driver (`needs-admin` or `needs-driver` in `pc.issues`), the processor, motherboard and fans pages say which readings are missing. The helper forwards every LHM sensor type the screens use, including drive throughput and current since 0.1.4; network adapters are not read.

## Manuals

Rig keeps the maker's own manual for each part (motherboard, laptop, graphics card, and parts the person names: case, power supply, cooler, memory, monitor, drive), finds the pages with useful diagrams, and lets the chat quote them by page. Each part's Manual tab on My PC finds, adds and opens its manual. The Manuals tab of My PC (`#manuals`, `packages/ui/src/manuals/ManualsTab.tsx`) searches every manual at once, shows one card per part, adds manuals for things Windows can't see (a monitor, the case), and lists each driver and BIOS with the maker's download page. Rig never installs them. Ctrl K also finds manuals, diagram pages and any page whose words match. The shared shapes are in `packages/core/src/manuals.ts`; the server's API is listed in `packages/core/src/api.ts`.

1. **Finding** (`POST /api/machines/:id/manuals/find`, `apps/server/src/manuals.ts`). The server first checks `manual_sources`, a cache shared by every account keyed by kind, maker and model (a manual's address is public, so two people with the same board don't both pay for a search). A miss is remembered for 7 days. Otherwise Claude looks with web search (5 uses) and web fetch (3), and answers with one `report_manual` call: found or not, the PDF's address and its title.
2. **Checking.** An address is used only when it's https with no user name or port, its host is the maker's own domain or a subdomain (one table of makers and their domains; for a maker not in it, the site's own name has to contain the maker's), and the file starts with `%PDF`. Each redirect is checked the same way. When an address fails, Claude is told why and may try another, a few times at most. A lookup that asks Claude counts as one of the day's chat questions; a cache hit is free.
3. **Downloading** (`GET …/manuals/:mid/pdf`). The app gets the PDF through the server, so it works whatever the maker's site allows. The address comes from the database, never from the request, and is checked against the maker again before every download. More than 60 MB is refused, by its size up front and by counting while it streams. If the maker's address is gone or no longer a PDF, the cache forgets it so the next lookup searches again. A PDF the person adds from their own files only has its details sent (`POST …/manuals`); the file stays on that device.
4. **Reading.** The app keeps a copy on the device, reads each page's text with pdf.js, marks the diagram pages, and sends the text back (`PUT …/pages`, up to 8 MB, the one route allowed more than 2 MB). The server keeps up to 600 pages of 6,000 characters, replacing the manual's old pages in one transaction. One manual per part: finding or adding again for the same part replaces the old one and its pages.
5. **Searching** (`GET …/manuals/search`, `0004_manuals.sql`). Postgres full-text search over each page's words twice: stemmed English, so "how do I connect the front panel" finds "connect the front panel switches", and word for word, so header names like F_PANEL, CPU_FAN, JRGB1 and M2_1 match exactly. A page matches either; best matches come first with a short snippet, matched words marked « ».
6. **In the chat.** The PC block lists each manual (part, title, page count, whether it's read, its diagram pages). The `search_manuals` tool returns the 4 best pages with about 1,500 characters of each, and each becomes a source that opens that page inside Rig (`rig:manual/<id>#page=<n>`). Claude is told to search a read manual first and say which page the answer is on, and, for a part with no manual yet, that it can be added on the part's Manual tab in My PC. Web search stays for everything else.

## Defaults chosen

- **Monorepo with pnpm workspaces.** The website and the app share every screen.
- **Desktop data in SQLite** in the app's data folder; history keeps 90 days, one point per ten minutes with the highest temperatures and fan speed in that window, whether it was busy, and the game in front for most of it.
- **Home charts come from history** (`packages/core/src/insights.ts`), in the viewer's local days. Idle is the processor's median while nothing heavy ran; typical and peak are the graphics card's busy median and highest reading (the processor's on a laptop or a desktop without graphics card readings). An evening runs 6 PM to 6 AM; a session is busy windows joined across at most one quiet window, and it ran hot when a part came within 6°C of its safe limit. Fans show the fastest speed per six-hour slice against the fastest slice shown.
- **The Games view comes from history too** (`packages/core/src/games.ts`): a game's sessions are its windows joined across at most one window without it; typical and peak use the same part as the home charts. Notes appear only when the history backs them: a game runs hotter or cooler than the others (at least 4°C apart, an hour of each), its peak came within 6°C of the safe limit, or its latest sessions run at least 3°C warmer than its earliest (four sessions or more). Frame rates and settings show only for games the client has measurements for; the demo's are marked as samples.
- **Server database is Postgres (Neon), not Cloudflare D1.** D1 stops at 10 GB per database and is meant to be split per user; one Postgres database can keep growing. Accounts stay in Rig's own database with Better Auth, so there's no per-user cost for sign-in.
- **Alerts** (`packages/core/src/alerts.ts`) are a table of rules over the live readings and the last 30 days of history: a part at its safe limit for two minutes, a fan that spun earlier reading 0 rpm while its part is hot, a drive under 10% free or under 20% of its life left, and a part running at least 5°C warmer in a game than in the same game two to four weeks ago. Whoever owns the live feed (the desktop, the demo) tracks them, so a problem has to last its rule's hold time, survives a two-minute dip, and keeps its start time if it comes back within 30 minutes. They ride on the PC view, so the website shows what the desktop saw. The desktop sends a Windows notification for a new one while its window isn't focused, at most once per alert every six hours. Each kind can be turned off per device, in the Notifications section of Settings, and the Health summary counts only the kinds left on. Like the findings, alert text is written in °C (a difference as a bare "5°") and shown in the unit the viewer picked.
- **Sign-in token in Windows Credential Manager**, not in a file.
- **Desktop sign-in through the browser** with a short code (OAuth device flow), so the app never handles a password.
- **Installer:** NSIS, installed for the current user (no admin prompt to install).
- **Helper ships self-contained** (no .NET install needed), about 70 MB.
- **Windows CI job runs on main and by hand** because Windows minutes count double on private repos.
